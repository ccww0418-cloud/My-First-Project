1 / 사용자에게 보이는 것

사용자는 이렇게 씁니다

기술을 몰라도 되는 부분입니다. 그냥 웹사이트입니다.

① 주소를 엽니다

화면이 뜨는 데 1초 이내

채팅창 하나와 예시 질문 버튼이 보입니다. 회원가입도 로그인도 없습니다.

② 편하게 씁니다

제목을 몰라도 됩니다

“출퇴근에 읽을 짧은 책”, “반전 있는 스릴러” 처럼 기분이나 상황만 말해도 됩니다.

③ 답과 카드를 받습니다

5~15초

추천 이유가 담긴 글이 먼저 나오고, 그 아래에 표지·평점·무료 다운로드 링크가 붙은 책 카드가 붙습니다.

기다리는 동안 뭘 보여주나

AI가 검색하는 데 시간이 걸립니다. 화면이 멈춘 것처럼 보이면 사용자는 떠납니다.
그래서 “지금 Google Books를 찾고 있고, 8권 찾았다”를 실시간으로 보여줍니다. 같은 대기 시간이 훨씬 짧게 느껴집니다.

언어

화면 기본 언어는 영어입니다. 오른쪽 위에서 한국어로 바꿀 수 있습니다.
챗봇 답변 언어는 화면 설정과 따로 움직입니다. 한국어로 물으면 한국어로, 프랑스어로 물으면 프랑스어로 답합니다.

추천한 책이 진짜 있는 책인가? 네. AI가 제목을 상상해서 말하는 것을 막았습니다. 반드시 도서 데이터베이스에서 검색해 확인된 책만 언급하게 했고, 화면의 카드 데이터는 AI를 거치지 않고 도서 API 원본이 그대로 옵니다.

3 / 실행 흐름

채팅 한 번에 실제로 일어나는 일

위에서 아래로 시간 순서입니다. 세로선 하나가 참여자 하나이고, 화살표는 “누가 누구에게 무엇을 보내는지”입니다.

4 / 동작 순서

“SF 소설 추천해줘” 한 마디가 지나가는 길

채팅 한 번에 아래 9단계가 순서대로 일어납니다.

  1. 브라우저가 요청을 보냅니다CloudFront 로 POST /api/chat. 내용은 HTTPS로 암호화됩니다.
  2. CloudFront가 길을 나눕니다/api/* 는 Lambda 쪽으로, 나머지는 S3 파일로. 이때 비밀 헤더를 붙여서 “정상 경로로 온 요청”임을 표시합니다.
  3. API Gateway → LambdaLambda가 깨어납니다. 처음 깨어날 때만 1초쯤 더 걸립니다(콜드 스타트).
  4. Lambda가 문지기 검사를 합니다비밀 헤더가 맞는지, 메시지가 비어 있지 않은지, 2,000자를 넘지 않는지.
  5. 사용 횟수를 확인합니다DynamoDB에 기록된 이 사람의 요청 수. 분당 10회 / 하루 150회까지.
  1. 내용 검사를 합니다책과 무관한 요청, 이상한 명령, 개인정보가 섞였는지 규칙 + AI 판정 2단계로 확인합니다.
  2. AI가 “무엇을 검색할지” 정합니다Bedrock의 Claude가 사용자 말을 읽고 도구를 고릅니다. 예: search_books(query:"science fiction", recent:true)
  3. 도서 API 4곳을 동시에 검색합니다결과를 합쳐 중복을 없애고, 책 카드는 AI를 거치지 않고 화면으로 바로 보냅니다. AI에게는 요약만 줘서 비용을 10분의 1로 줄입니다.
  4. AI가 추천 글을 씁니다검색된 책만 근거로 이유를 설명합니다. 대화 기록을 DynamoDB에 저장하고 끝.
왜 29초·18초 같은 숫자가 중요한가. API Gateway는 29초 안에 답이 안 오면 포기하고 오류를 냅니다. 그래서 검색에 쓸 시간을 18초로 정해두고, 넘으면 검색을 멈추고 “지금까지 찾은 것으로 답하기”로 전환합니다. 이렇게 해야 사용자가 오류 화면 대신 답을 받습니다.

5 / AWS 서비스

쓴 AWS 서비스 8개 — 일상에 비유하면

이름은 낯설지만 하는 일은 단순합니다.

CloudFront

배달망 (CDN)

전 세계 수백 곳에 복사본을 두고 가장 가까운 곳에서 내려줍니다.

비유 전국 편의점 물류망. 서울 사람은 서울 창고에서 받습니다.

S3

파일 창고

화면을 구성하는 HTML·JS·CSS 파일을 보관합니다. 계산은 안 합니다.

비유 무한히 넓은 창고. 꺼내 갈 때만 돈을 냅니다.

API Gateway

접수 데스크

바깥 요청을 받아 Lambda에 넘기는 정문입니다.

비유 민원 창구. 서류를 받아 담당자에게 전달합니다.

Lambda

일하는 직원

실제 로직이 도는 곳. 요청이 올 때만 켜지고 끝나면 사라집니다.

비유 호출하면 오는 프리랜서. 대기 시간엔 급여가 안 나갑니다.

Bedrock

AI 이용 창구

Claude 같은 AI 모델을 API로 빌려 씁니다. 모델을 직접 설치할 필요가 없습니다.

비유 통역사 파견 서비스. 쓴 분량만큼 계산합니다.

DynamoDB

장부 (데이터베이스)

대화 기록·검색 캐시·사용 횟수를 저장합니다. 정해둔 시간이 지나면 자동 삭제됩니다.

비유 포스트잇 메모판. 오래된 건 스스로 떨어집니다.

Parameter Store

비밀 금고

외부 API 키를 코드에 적지 않고 여기 넣습니다. 암호화되고 요금이 없습니다.

비유 열쇠 보관함. 필요할 때만 꺼내 봅니다.

CloudWatch · SNS

CCTV + 경보

오류·응답지연·비용 급증을 감시하고 메일로 알립니다. 로그도 여기 쌓입니다.

비유 화재 감지기와 연결된 문자 알림.

왜 리전이 us-east-1(미국 버지니아)인가. AI 모델 종류가 가장 많은 지역이라 선택했습니다. 화면 파일은 사용자와 가까운 곳에서 나가므로 어디서 접속해도 빠릅니다. 유럽에서 접속하면 오히려 한국보다 응답이 빠릅니다 (파리↔버지니아가 서울↔버지니아보다 가깝습니다).

6 / 외부 데이터

도서 API를 왜 4개나 쓰나

한 곳으로는 부족합니다. 각자 잘하는 게 다르고, 하나가 죽어도 서비스가 살아야 합니다.

이름이것만 줄 수 있는 것약점키 / 한도
Google Books 가장 많은 책, 표지 이미지, 페이지 수 평점·분위기 정보가 없음 API 키 필요 · 하루 1,000회
Open Library 주제 분류, 출간연도 범위 검색 (신간 찾기의 핵심) 메타데이터 오류가 있음 (9999년 같은 값) 키 없음 · 연락처 표기 요구
Hardcover 독자 평점, 분위기 태그, 내용 주의(폭력·자해 등) 수록 도서 수가 적음 토큰 필요 · 분당 60회
Project Gutenberg 무료 전문 다운로드 (EPUB·TXT 실제 파일) 저작권 만료 도서만 (대부분 1929년 이전) 키 없음

합치는 방법

같은 책이 4번 나오면 안 됩니다. ISBN이 같으면 같은 책으로 합치고, ISBN이 없으면 제목+저자를 정규화해 비교합니다.

한 곳이 죽으면

4곳을 동시에 부르고 성공한 것만 씁니다. Gutenberg가 응답을 안 하면 Open Library의 무료 도서 검색으로 대신합니다.

같은 검색을 또 하면

DynamoDB에 6시간 저장해 뒀다가 그대로 씁니다. 외부 API 한도를 아끼고 응답도 1초 → 0.01초로 빨라집니다.

“추천 이유”가 어디서 나오나. Hardcover의 분위기 태그입니다. “독자들이 reflective, emotional 이라고 평가했고 평점은 4.3/5” 같은 근거를 댈 수 있어서 AI가 막연한 칭찬 대신 실제 데이터를 인용합니다.

7 / 데이터

데이터는 어디에, 얼마나 저장되나

DynamoDB 테이블 딱 1개로 네 가지 일을 합니다. 전부 자동으로 지워집니다.

용도저장 형태보관 기간왜 이렇게 했나
대화 기록SESSION#{세션ID}24시간“그 중 제일 짧은 건?” 같은 후속 질문을 이해하려면 앞 대화가 필요합니다.
검색 캐시CACHE#{검색조건}6시간같은 질문에 외부 API를 또 부르지 않게. 한도 절약 + 속도.
사용 횟수RL#{IP주소}2분 / 25시간한 사람이 과도하게 쓰는 것을 막습니다 (분당 10회, 하루 150회).
정책 판정 캐시CACHE#policy.topic24시간같은 문장을 반복 검사하지 않도록.

테이블을 1개만 쓴 이유

DynamoDB는 테이블마다 요금과 관리 항목이 붙습니다. 키 앞에 용도를 붙이는 방식(SESSION#, CACHE#)으로 한 테이블에 모으면 관리할 것이 하나로 줄고 비용도 적습니다. 실무에서 쓰는 단일 테이블 설계입니다.

자동 삭제(TTL)를 켠 이유

지우는 코드를 따로 쓰지 않아도 AWS가 만료된 항목을 알아서 지웁니다. 저장 요금이 계속 늘지 않고, 개인정보를 오래 갖고 있지 않게 됩니다.
주의 24시간이 지난 대화는 조회할 수 없습니다. 기록을 남기려면 별도 저장이 필요합니다.

비밀 값은 여기 두지 않습니다. 외부 API 키와 오리진 비밀은 Parameter Store에 암호화해서 넣고, Lambda가 시작할 때 읽어 5분간만 메모리에 들고 있습니다. 코드나 Git에는 키가 없습니다.

8 / 보안과 비용

안전장치 — 두 종류를 4겹으로

챗봇은 “이상한 말”과 “요금 폭탄”이 두 가지 큰 위험입니다.

이상한 요청 막기 4겹

1겹 · 규칙 검사 — 정규식 20여 개로 “이전 지시를 무시해”, 주민번호, 폭탄 제조법 등을 즉시 차단. 네트워크 호출 없이 0.001초.

2겹 · AI 판정 — 규칙을 통과했지만 책과 무관한 요청인지 AI가 한 단어(ALLOW/BLOCK)로 판정.

3겹 · 시스템 프롬프트 — AI에게 “책 얘기만 하라, 검색으로 확인한 책만 말하라”를 지시.

4겹 · WAF — 같은 IP가 5분에 300회(채팅은 100회) 넘게 부르면 AWS가 입구에서 차단.

요금 폭탄 막기 4겹

1겹 · 앱 사용 제한 — 한 IP당 분당 10회, 하루 150회.

2겹 · WAF 차단 — 위와 동일한 규칙이 AWS 입구에서 먼저 걸러냅니다.

3겹 · Lambda 동시 실행 10개 제한 — 갑자기 트래픽이 몰려도 동시에 10개까지만 돕니다.

4겹 · Budgets 예산 알림 — 월 $100 / Bedrock만 $50 기준으로 50%·80%·예상 100%에서 메일이 옵니다.

S3를 비공개로

버킷을 인터넷에 열지 않았습니다. CloudFront만 읽을 수 있게 권한을 걸었습니다(OAC). 주소를 알아도 직접 접근 불가.

비밀 헤더로 우회 차단

CloudFront가 요청에 비밀 값을 붙이고 Lambda가 확인합니다. Lambda 주소를 알아도 CloudFront를 건너뛰고 부를 수 없습니다.

AI가 HTML을 못 넣게

AI 답변을 화면에 그릴 때 HTML로 해석하지 않습니다. 외부 도서 데이터에 악성 코드가 섞여도 글자로만 표시됩니다.

솔직하게 남은 것. 공개 서비스로 운영한다면 Bedrock Guardrails(AWS 공식 안전장치)를 추가하고, 유럽 사용자를 받으려면 개인정보 처리방침이 필요합니다. 짧은 실습 기간에는 위 4겹으로 충분하다고 판단했습니다.

됩니다. 이미 있으면 “건너뜀”으로 넘어가고 바뀐 것만 고칩니다(멱등성). 실패한 지점부터 다시 돌리면 됩니다.
